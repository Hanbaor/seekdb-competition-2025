## 2. 为什么需要回表

### 2.1 当前的数据流

```
倒排索引扫描（ObDASTextRetrievalIter）
  ↓ 返回
doc_id + relevance
  ↓
ObDASFuncDataIter::add_doc_id()
  ↓ 硬编码过滤
if (doc_id > 1000) skip
  ↓ 保留的 doc_id
[doc_001, doc_005, doc_100, ...]
  ↓
ObDASFuncDataIter::inner_get_next_row()
  ↓
========== 问题在这里！==========
main_lookup_iter_->get_next_row()  ← 回表查询主表
  ↓
查询：SELECT id, base_id, docid_col FROM items1 WHERE rowid = ...
  ↓ 10ms（随机IO）
返回：id, base_id, docid_col
  ↓
应用过滤：if (id < 1000 && base_id IN (...))
  ↓
返回最终结果
```

**问题**：
- 即使在 `add_doc_id()` 中已经过滤了一次（硬编码的 `> 1000`）
- 仍然需要回表查询 `base_id` 等其他字段
- 因为倒排索引中**没有存储**这些字段

## 3. 屏蔽回表的三种方案

### 方案A：设置标志跳过回表（最简单，适合硬编码验证）

**核心思想**：添加一个标志，告诉系统"已经完成过滤，不需要回表"

```cpp
// 在 ObDASFuncDataIter 中添加标志
class ObDASFuncDataIter {
private:
  bool scalar_filter_done_;  // ← 新增：标量过滤已完成标志
  // ...
};

// 初始化时设置（硬编码）
int ObDASFuncDataIter::inner_init(ObDASIterParam &param)
{
  // ...原有初始化...
  
  // ========== 硬编码：如果有嵌入字段，跳过回表 ==========
  // TODO: 后续改为从配置或 ctdef 读取
  scalar_filter_done_ = true;  // ← 硬编码设置为 true
  
  return ret;
}

// 在 inner_get_next_row() 中跳过回表
int ObDASFuncDataIter::inner_get_next_row()
{
  int ret = OB_SUCCESS;
  
  // ========== 修改：如果已经完成过滤，跳过回表 ==========
  if (!scalar_filter_done_ && main_lookup_iter_) {
    // 只有在 scalar_filter_done_ = false 时才回表
    if (OB_FAIL(main_lookup_iter_->get_next_row())) {
      if (OB_ITER_END != ret) {
        LOG_WARN("fail to get next row for main lookup table", K(ret));
      } else {
        ret = OB_SUCCESS;
      }
    }
  }
  
  // 全文检索迭代器（已经包含了嵌入字段和过滤）
  for (int64_t i = 0; OB_SUCC(ret) && i < iter_count_; i++) {
    if (OB_FAIL(tr_merge_iters_[i]->get_next_row())) {
      // ...
    }
  }
  
  return ret;
}

// 批量版本也需要修改
int ObDASFuncDataIter::inner_get_next_rows(int64_t &count, int64_t capacity)
{
  int ret = OB_SUCCESS;
  int64_t main_lookup_count = 0;
  int64_t tr_merge_count = 0;
  
  // ========== 修改：跳过回表 ==========
  if (!scalar_filter_done_ && OB_NOT_NULL(main_lookup_iter_)) {
    while (OB_SUCC(ret) && main_lookup_count == 0) {
      if (OB_FAIL(main_lookup_iter_->get_next_rows(main_lookup_count, capacity))) {
        // ...
      }
    }
  }
  
  // ...后续逻辑...
}
```

**优点**：
- ✅ 实现简单，只需要加一个 if 判断
- ✅ 不影响现有逻辑
- ✅ 适合快速验证

**缺点**：
- ⚠️ 需要确保 docid_col 能从全文检索迭代器获取

---

### 方案B：不创建 main_lookup_iter_（根本解决方案）

**核心思想**：如果有嵌入字段，在构建迭代器树时就不创建 `main_lookup_iter_`

```cpp
// 在创建迭代器树时（ob_das_iter_utils.cpp）

int create_domain_lookup_sub_tree(...)
{
  // ...
  
  // ========== 检查是否需要主表查询 ==========
  bool need_main_lookup = true;
  
  // 如果有嵌入字段，不需要主表查询
  if (has_embedded_scalar_fields(ir_scan_ctdef)) {
    need_main_lookup = false;
    LOG_INFO("skip main lookup because scalar fields are embedded");
  }
  
  // 只在需要时创建主表查询迭代器
  if (need_main_lookup) {
    // 创建 main_lookup_iter_
    // ...
  }
  
  return ret;
}
```

**优点**：
- ✅ 彻底避免回表（连迭代器都不创建）
- ✅ 节省内存和初始化开销

**缺点**：
- ⚠️ 需要修改迭代器树构建逻辑（复杂）
- ⚠️ 需要确保所有需要的字段都能从其他地方获取

---

### 方案C：混合方案（推荐用于验证）

**核心思想**：先用方案A快速验证，后续优化时改为方案B

**第一阶段：硬编码验证**

```cpp
// 步骤1：在 ObDASFuncDataIter 中添加硬编码标志

// 步骤2：在 inner_get_next_row() 中跳过回表

  // 回表（现在不会执行）
}

// 步骤3：确保 docid_col 能从全文检索迭代器获取
// （需要在 ObDASTextRetrievalIter 的输出中包含 docid_col）
```

**第二阶段：条件下推**

```cpp
// 从 ctdef 读取标志（替代硬编码）
scalar_filter_done_ = ir_ctdef->has_embedded_scalar_fields_;
```

**第三阶段：优化迭代器树**

```cpp
// 不创建 main_lookup_iter_
if (!has_embedded_scalar_fields(ir_scan_ctdef)) {
  // 创建 main_lookup_iter_
}
```

## 4. 关键问题：docid_col 从哪里来？

### 4.1 问题说明

SQL 查询需要返回 `docid_col`：

```sql
SELECT docid_col, MATCH(...) as _score
FROM items1
WHERE ...
```

**当前流程**：
- 倒排索引返回内部 `doc_id`（数字ID）
- 回表查询主表，获取 `docid_col`（字符串，如 'doc_001'）

**如果屏蔽回表**：
- 必须从其他地方获取 `docid_col`

### 4.2 解决方案

#### 方案1：嵌入到倒排索引（推荐）

```cpp
struct EnhancedPosting {
  uint64_t doc_id;           // 内部数字ID
  float relevance;
  uint64_t cached_id;        // 嵌入的 id
  uint32_t cached_base_id;   // 嵌入的 base_id
  // ========== 新增：嵌入 docid_col ==========
  ObString cached_docid_col; // 嵌入的 docid_col（如 'doc_001'）
};
```

**在倒排索引构建时**：
```cpp
posting.cached_docid_col = row.docid_col;  // 嵌入
```

**查询时直接使用**：
```cpp
ObString docid_col = get_cached_docid_col();
// 无需回表！
```

#### 方案2：使用映射表

创建一个轻量级的 doc_id → docid_col 映射：

```cpp
// 在内存中维护映射（或使用辅助表）
ObHashMap<uint64_t, ObString> doc_id_to_docid_col_;

// 查询时
ObString docid_col;
doc_id_to_docid_col_.get(doc_id, docid_col);
```

#### 方案3：修改返回字段

如果 `docid_col` 和内部 `doc_id` 其实是一对一的，可以直接使用 `doc_id`：

```cpp
// 返回 doc_id 而不是 docid_col
// （如果业务允许）
```

```cpp
posting.cached_base_id = hash(row.base_id);
posting.cached_docid_col = row.docid_col;

while (scan posting) {
  cached_id = ...;
  cached_base_id = ...;
  
  // 硬编码过滤

  if (cached_base_id != hash('base_1') && 
      cached_base_id != hash('base_2')) continue;

// 3. 在 ObDASFuncDataIter 中屏蔽回表
bool scalar_filter_done_ = true;  // 硬编码

}
```
