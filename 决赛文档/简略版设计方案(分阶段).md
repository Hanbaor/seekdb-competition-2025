## 二、你想要的新路径目标

你现在的目标可以归纳成：

1. **doc_id 只经过一次 FTS 倒排** 得到。
2. **所有标量列（id/base_id/docid_col/...）全部来自 `g_fts_scalar_cache`**，比赛场景中视为 100% 命中，不再真正回表。
3. **过滤/排序/限制（WHERE + ORDER BY + LIMIT）尽量在“缓存已经补齐标量之后”统一做**，不要再走一遍 TableScan/Filter 的复杂链路。
4. **查询 SQL 不改（比赛要求固定）**，改的是执行计划与 DAS 迭代器路径。

结合现有代码，**完全新造一个大算子从零接管执行引擎成本太高**；更现实、更符合当前结构的方案是：

> 把 [ObDASCacheLookupIter](cci:2://file:///home/tian/seekdb/src/sql/das/iter/ob_das_cache_lookup_iter.h:48:0-115:1) 升级成一个真正的 “FTS Scalar Fetch” 终端算子，用它来实现完整的  
> `doc_id → g_fts_scalar_cache → 填各个输出 expr → 输出行`，  
> 并尽可能**不再依赖后面的 data_table_iter 回表**。

这样你不会和 TableScan/Filter 深度纠缠，改动主要集中在 DAS / FTS 这几个文件。

## 三、详细实现计划（分阶段，可落地）

### 阶段 0：前提与约束确认

- **数据只读**：比赛期间主表不会更新 → `g_fts_scalar_cache` 可以在导入/建索引阶段一次性填满。
- **缓存 100% 命中假设**：运行时逻辑可以把 miss 当作异常/兜底分支，而不是常规路径。
- **只针对 FTS 这条路径**：不去改通用 TableScan/DAS 的默认实现。

### 阶段 1：缓存构建与预热

- 文件：`src/sql/das/ob_fts_scalar_cache.{h,cpp}` + 你已有的构建脚本。
- 规划：
  - 在导数据或建全文索引的流程里（可以是单独的初始化 SQL/脚本），**遍历整表**，对每个 doc_id 调用：
    ```cpp
    g_fts_scalar_cache.add_mapping(doc_id, id, base_id, docid_col);
    ```
  - 这样运行查询时，[get_scalar_fields(doc_id, fields)](cci:1://file:///home/tian/seekdb/src/sql/das/ob_fts_scalar_cache.cpp:99:0-115:1) 理论上永远成功。
- 这一步不涉及 OceanBase 内部大量改动，更像是“比赛环境初始化脚本”。

### 阶段 2：给 `result_output_` 挂列标识（关键）

**目的**：让 [ObDASCacheLookupIter](cci:2://file:///home/tian/seekdb/src/sql/das/iter/ob_das_cache_lookup_iter.h:48:0-115:1) 在 `OUTPUT_ROWS` 阶段，不再靠 slot/type 猜测，而是精确知道：

- 哪个 expr 是 `id`，哪个是 `base_id`，哪个是 `docid_col`，哪个是 `_score` 等。

#### 2.1 在 CTDef/Expr 上挂标识

- 涉及文件：

- 设计思路：
  - 在 FTS 路径生成 CTDef 的地方（[generate_text_retrieval_dep_exprs](cci:1://file:///home/tian/seekdb/src/observer/table/fts/ob_table_fts_cg_service.cpp:70:0-216:1) / TSC CG），为三类列打 tag：

  - 实现方式可以有两种：
    - **简单粗暴**：在 [ObExpr](cci:2://file:///home/tian/seekdb/src/sql/engine/expr/ob_expr.h:444:0-970:1) 的某个 unused 字段或 `extra_info_` 里塞一个 `int8_t tag`（比赛 hack，可以接受）。

      ```cpp
      struct FTSScalarSlot {
        int64_t result_output_idx;
        FTSScalarKind kind; // ID/BASE_ID/DOCID_COL
      };
      ```
      然后在 [ObDASCacheLookupIter](cci:2://file:///home/tian/seekdb/src/sql/das/iter/ob_das_cache_lookup_iter.h:48:0-115:1) 中通过 `lookup_ctdef_->fts_scalar_slots_` 进行 mapping。

- 可行性：
  - `ObTableFtsExprCgService` 已经能从 schema 中区分“docid 列、fulltext 列、word_count, doc_length”等，这里再加一层“哪一个是 base_id/id/docid_col”是自然的扩展。
  - 你已经有 `FTS Cache Schema Probe` 日志，实现前可以再看一遍 `expr->datum_meta_.type_` 输出，确认各列顺序。

### 阶段 3：把 [ObDASCacheLookupIter](cci:2://file:///home/tian/seekdb/src/sql/das/iter/ob_das_cache_lookup_iter.h:48:0-115:1) 变成真正的 FTS Scalar Fetch 算子

这一步是核心，也是你想要的“doc_id→缓存→过滤→输出”的落地点。

#### 3.1 改造 `OUTPUT_ROWS` 阶段填充逻辑

- 文件：[sql/das/iter/ob_das_cache_lookup_iter.cpp](cci:7://file:///home/tian/seekdb/src/sql/das/iter/ob_das_cache_lookup_iter.cpp:0:0-0:0)
  - 函数：[ObDASCacheLookupIter::inner_get_next_rows(int64_t &count, int64_t capacity)](cci:1://file:///home/tian/seekdb/src/sql/das/iter/ob_das_functional_lookup_iter.cpp:185:0-211:1)
  - 你现在的关键代码已经在 `OUTPUT_ROWS` case 里：
    ```cpp
    uint64_t doc_id = cached_doc_ids_.at(i);
    ScalarFields fields;
    int cache_ret = g_fts_scalar_cache.get_scalar_fields(doc_id, fields);
    if (OB_SUCC(cache_ret)) {
      // 当前用 type/slot heuristic 填 expr
    }
    ```
- 调整为：
  - 使用 **阶段 2 挂好的列标识**：
    ```cpp
    const ObDASScanCtDef *lookup_ctdef = static_cast<const ObDASScanCtDef*>(lookup_ctdef_);
    for (每个 result_output[j]) {
      ObExpr *expr = lookup_ctdef->result_output_.at(j);
      switch (expr->fts_scalar_tag_) {
        case FTS_SCALAR_ID: datum.set_uint(fields.id_); break;
        case FTS_SCALAR_BASE_ID: 复制 fields.base_id_; break;
        case FTS_SCALAR_DOCID_COL: 复制 fields.docid_col_; break;
        default: 按原逻辑（score、其他表达式等）
      }
    }
    ```
  - 这样做之后：**只要 result_output_ 中出现了 base_id/id/docid_col 对应的 expr，就一定能由缓存精确填好**，不再靠 slot 猜。

#### 3.2 尽量绕开真正回表

- [ObDASCacheLookupIter](cci:2://file:///home/tian/seekdb/src/sql/das/iter/ob_das_cache_lookup_iter.h:48:0-115:1) 还继承了 `ObDASLocalLookupIter`，状态机中有 `DO_LOOKUP` 会调用 [do_index_lookup()](cci:1://file:///home/tian/seekdb/src/sql/das/iter/ob_das_functional_lookup_iter.cpp:235:0-316:1) 触发真正 TableScan。
- 你的设想是“缓存永不 miss”，那可以在 `OUTPUT_ROWS` 中：
  - 命中缓存时 **不再把 `state_` 切回 INDEX_SCAN/DO_LOOKUP**，而是在所有 doc_id 处理完后直接转为 FINISHED：
    ```cpp
    if (hit_count > 0) {
      state_ = FINISHED;
    } else {
      // 理论上不会发生；发生时可以 fallback 到原来的 check_index_lookup 流程
    }
    ```
  - 这样，在“正常场景”下，DAS 层 **实际上完全不会触发真正回表**，只在极端异常（cache 不完整）时兜底。

- 从架构角度看，这就已经是一个“FTS Scalar Fetch” 终端算子了，只是名字还是 [ObDASCacheLookupIter](cci:2://file:///home/tian/seekdb/src/sql/das/iter/ob_das_cache_lookup_iter.h:48:0-115:1) 而已；你无需额外再造一套全新类层次。

### 阶段 4：谓词与排序位置的安排

你担心“上层算子看不到 base_id/id 就没法过滤”，在这套方案里：

- **过滤**：
  - 如果谓词已经被 FTS 路径推到 IR 层（如部分 match_filter），继续保持。
  - 对于 SQL 里的 `base_id in (...)`、`id < 1000`，可以有两种策略：
    - **策略 A（简单）**：仍由上层 Filter 算子执行，但此时 base_id/id 已经由缓存填好，上层算子只是在“现成值”上 eval，不需要再触发行访问。
    - **策略 B（更激进）**：在 [ObDASCacheLookupIter](cci:2://file:///home/tian/seekdb/src/sql/das/iter/ob_das_cache_lookup_iter.h:48:0-115:1) 中自己 eval 这些谓词（需要拿到对应的 ObExpr 和常量表达式），不满足的 doc_id 直接跳过，不进入输出。这会让上层 Filter 几乎什么都不用做，但改动会更大（要在 DAS 层 eval 表达式）。

- **排序/Limit**：
  - BM25 分数（`relevance_expr`/`relevance_proj_col_`）是在 FTS 路径里就计算好的，倒排/IR 这层已经在控制 doc_id 顺序。
  - 你可以选择：
    - 让 IR 层按 score 已经排好序，[ObDASCacheLookupIter](cci:2://file:///home/tian/seekdb/src/sql/das/iter/ob_das_cache_lookup_iter.h:48:0-115:1) 只负责补标量。
    - 或者由 IR 层只产出 doc_id+score，[ObDASCacheLookupIter](cci:2://file:///home/tian/seekdb/src/sql/das/iter/ob_das_cache_lookup_iter.h:48:0-115:1) 再结合 base_id/id 做二次排序（一般没必要）。

就比赛来说，**优先选择策略 A**：不改变 Filter 位置，只是确保 Filter 所需的列都由 cache 填好，Filter 不会触发任何回表。

## 四、小结

- 从当前项目结构来看，**最可行的“完全走缓存路径”方案**，是把 [ObDASCacheLookupIter](cci:2://file:///home/tian/seekdb/src/sql/das/iter/ob_das_cache_lookup_iter.h:48:0-115:1) 强化成一个“FTS Scalar Fetch” 终端算子：

  - 正常情况下不再进入真正回表逻辑，只保留兜底分支。
- 这一套设计不需要从零造一个新迭代器类型，但语义上已经是“doc_id → 缓存 → 过滤/投影 → 输出”的新路径，最大限度绕开了 TableScan/Lookup 的传统机制。
